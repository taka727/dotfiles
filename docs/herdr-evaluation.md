# Herdr 導入検討メモ

[herdr.dev](https://herdr.dev/) / [GitHub](https://github.com/herdrdev/herdr) の調査と、
自分の環境（WezTerm + claudecode.nvim + AWS CLI環境）に対する導入メリットの評価。
**まだ導入していない。検討段階のメモ。**

## Herdrとは

Rust製・単一バイナリのバックグラウンドサーバーとして動く「コーディングエージェント向けターミナルマルチプレクサ」。
tmux/Zellijに近いが、Claude Code / Codex / Cursor などエージェントの出力を解析して
working / blocked / idle / done の状態を自動検知し、ダッシュボード的に一覧できる点が差別化ポイント。
OSS（Apache 2.0）、GitHub Star 29.5k。

```bash
brew install herdr   # または curl -fsSL https://herdr.dev/install.sh | sh
```

## 自分の現在の環境

- `.config/wezterm/keymaps.lua` — LEADER+r/d でペイン分割、LEADER+; で選択、LEADER+w で入れ替え、
  LEADER+e でリサイズモードと、すでにWezTerm標準機能だけで手動のペイン運用を組んでいる
- `.config/nvim/lua/plugins/claude.lua`（2026-08-13導入）— `claudecode.nvim` によりClaude Codeを
  Neovim統合し、diff承認フローで編集競合を解消済み。つまり主な使い方は
  **「Neovim内でIDE統合されたClaude Code」であり、独立した複数のCLIペインを並列で回す使い方ではない**
- `docs/aws-cli-setup.md` — `aws-vault` / `session-manager-plugin` を導入済み。EC2へのSSM接続基盤はあるが、
  現時点でリモートサーバー上でエージェントを動かす運用はしていない
- 単一MacBook + AeroSpace（ウィンドウマネージャ）構成。マルチマシン/リモート常時稼働の前提は今のところない

## 環境に対する導入メリットの評価

### 効果が限定的な理由
- Herdrの目玉機能（複数エージェントのworking/blocked一覧）は、**複数の独立したCLIエージェントを並列で
  走らせて初めて効いてくる**。現状はNeovim統合1セッションが主戦場なので、恩恵を受ける場面が少ない
- `claudecode.nvim` はNeovim内の埋め込みターミナル経由でClaude Codeを起動する構成のため、
  Herdrのスクリーン検出（生のCLI出力を解析する方式）とは相性の検証が必要。素のCLIペインで
  `claude` を直接叩く運用と同じようには state 検知が効かない可能性がある
- WezTermのペイン分割・選択・入れ替えは自前のキーマップで既にひととおり揃っており、
  2〜3ペイン程度の規模なら現状で困っていない

### 効果が見込める場面（限定的だが実在する）
1. **WezTerm自体のクラッシュ/誤 Cmd+Q からの保護**
   現状はGUIプロセス（WezTerm）とペインのライフサイクルが直結しているため、アプリが落ちる／終了すると
   実行中のClaude Codeタスクごと失われる。Herdrはサーバー・クライアント分離のため、ターミナルアプリ側に
   何かあってもエージェントのプロセスは生き残る。頻度は低いが、起きたときの損失（作業のやり直し）が大きい
2. **AWS/SSMでのリモート開発に踏み出したとき**
   `session-manager-plugin` はすでに入っているので、EC2上でエージェントを動かす運用を始めた場合、
   SSH/SSM切断で作業が止まらない・後から再アタッチできるというHerdrの強みがそのまま活きる。
   現状の投資（aws-vault, session-manager-plugin）と相性が良い
3. **並列タスクが増えたとき**
   dotfiles以外の複数プロジェクトを掛け持ちして、それぞれでClaude Codeを別ペインで走らせる運用に
   移行した場合、blocked状態の自動検知で「どのペインが入力待ちか」を目視確認せずに把握できる

## 作業効率への影響（見積もり）

- **今すぐの効率改善**: 小〜中程度。現状の使い方（Neovim統合の単一セッション中心）では
  WezTermの既存ペイン運用を置き換えるほどの明確な差は出にくい
- **保険としての価値**: あり。クラッシュ/誤終了からの復旧という「めったに起きないが起きると痛い」
  ケースに効く。導入コストが `brew install herdr` 一発なので、保険としてのコストパフォーマンスは高い
- **将来的な伸びしろ**: リモート開発（EC2/SSM）や複数プロジェクト並列運用に移行した場合に大きく伸びる。
  現状の構成からの延長線上にある投資なので、無駄になりにくい

## 結論

現状の「Neovim統合・単一マシン・ペイン2〜3枚」という使い方の範囲では、緊急に導入するほどの
明確な効率化効果はない。一方で導入コストがほぼゼロなので、

- すぐに使い倒す前提での導入というより、**保険（クラッシュ耐性）として軽く試す**
- 本格的な効果は「AWS/SSMでのリモートエージェント運用」または「複数プロジェクトの並列エージェント運用」を
  始めたタイミングで再評価する

という位置づけが妥当。当面は他の検討中タスク（ターミナルブラウジング環境、Karabinerリマップ設定）と
並べて保留し、上記のいずれかの運用変化が起きたら改めて導入を検討する。
